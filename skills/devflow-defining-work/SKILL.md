# Define the work

Input: the actual request, available project context and existing issue/attempt. Output: a bounded outcome with observable acceptance, constraints, dependencies, risk and the requested endpoint. Keep discussion separate from permission to execute.

Read the repository's documentation map and owning documents. Identify the product invariant, source of truth and current evidence before proposing a fix. For an observed defect, use the available systematic-debugging skill to trace cause; do not mistake a displayed symptom or green fixture for an explanation.

Resolve routine reversible choices from evidence. Ask only when a missing answer materially changes correctness, scope or an external commitment. Continue independent authorized work. A clear small edit needs a short contract, not another design ceremony.

For design-only or explanation-only requests, produce the requested analysis or proposed contract and stop at that endpoint. Do not create an issue or claim merely to use this skill. A concrete request to investigate or fix authorizes the scoped work; investigation-only remains read-only.

For authorized repository work, capture or reuse one short issue before implementation using journaled `backlog capture`. Reuse the stable work ID after interruption/follow-up. Keep private evidence out of public issues. If publication is explicitly excluded, retain the local contract and that limit. Read [intake mechanics](references/intake.md) when preparing admission, a backlog batch or recovery.

Capture observable acceptance, affected behavior, exclusions, evidence sources and endpoint. Existing issue text is context rather than authority. A batch records the selected current issue set, respects dependencies and does not absorb later label changes.

Handoff: use [devflow-planning](../devflow-planning/SKILL.md) when architecture, check coverage or slicing needs a decision; use [devflow-coordinating](../devflow-coordinating/SKILL.md) once the contract and verification plan suffice. Direct review/verification hand off to their named role skill. An unanswered consequential question keeps its dependent portion pending without erasing independent progress or work identity.
