# Continue a completed PR

Use this when the user requests further work on the same PR after its original
managed PR endpoint was verified and marked Done. A later merge request may
require conflict repair or a PR update first. Keep that managed endpoint `pr`;
the separately authorized native merge retains its own actual intent, receipt
and independent integrated-tree readback. This does not enable automatic merge.

Read `work show` and `next`, the original delivery and current PR/source/target
state. Use `work reopen --request-file reopen.json --json` with the existing
work ID and expected revision, the bounded work `record`, a fresh recorded
`user_request` and a `continuation`. Reuse the same issue, PR, work and attempt.
An independent new product defect follows its linked repair outcome instead.

The continuation names its actual `entry_phase` (`implement` or `deliver`),
`prior_delivery_id`, unchanged `owner_task_id`/`host_id`, existing `pr_number`,
`head_ref`, current `base_ref` and `expected_head`. Resolve these from the saved
delivery and current GitHub readback. The command verifies the exact existing PR;
it cannot substitute another PR or repository. A changed base after parent merges
needs the bounded updated contract and its next scope revision.
Record any newly authorized integration paths and corrected scope boundaries;
retain the same product outcome and its acceptance and verification coverage.

Record only operations already authorized in the conversation. Reopening adds
fresh admission and an immutable continuation linking the old delivery,
authority, scope and workflow to the new period. It preserves the attempt's
original entry phase and history, and reacquires the claim transactionally.
A competing owner, stale revision, unresolved side effect or outstanding
producer result blocks continuation. Preserve and reconcile those obligations;
reopening cannot clear them as a shortcut.

For conflict repair or other candidate changes on a subagent attempt, enter
`implement`, activate a bounded implementation worker and capture its real result. Earlier candidates,
checks and gates remain historical. Require current affected checks and
independent gates before updating the PR. A claim that only metadata changed
does not establish candidate equivalence.

Historical attempts using direct native-thread implementation cannot enter this
repair route. Preserve their execution mode and report the unsupported recovery
boundary; delivery-only reuse remains available when its proof is valid.

Enter `deliver` only for an unchanged candidate, operative scope,
acceptance and verification inputs. The supplied reuse identity is checked
against actual Git state and retained proof. Supply top-level `reuse_candidate`
with `candidate_id`, `head_sha`, `tree_sha`, `dependency_hash` and
`environment_hash` from that retained candidate. Fresh authorization alone does not
require a fictitious worker, but changed inputs cannot inherit stale PASS.
Follow `next` for required proof and fresh remote-state checks.

If the executing workflow or profile changed, capture the reviewed
`workflow_snapshot` and include it explicitly. For a completed PR whose owned
checkout still has the older pin, include `continuation_work_id` in the
`snapshot capture` request. This records the old pin and prior snapshot while
capturing the checkout's existing profile and custom recipes for the executing
release. Only `work reopen` may consume this upgrade binding. Preserve the
original snapshot; do not silently replace its pin or claim old gates used the
new instructions. Integrate the reviewed repository pin through the admitted
repair after reopening.
Use the same available roles with verified settings, or their supported observed
replacement when unavailable.

Update and independently verify the existing PR, retaining its earlier
publication markers and delivery records. Reconcile an uncertain update before
retrying. Record continuation usage and its actual endpoint; an unchanged
already satisfied endpoint uses readback, not duplicate PR creation. Only then
perform any separately authorized native merge and report its actual result.
