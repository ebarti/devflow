# Verified intake and execution admission

Version 0.2.0 blocks managed execution until an independently trusted intake verifier is available. The shipped CLI has no authenticated first-party intake or human-validation adapter. `doctor` therefore reports `trusted_intake_unavailable`, `human_validation_unavailable`, `execution_enabled: false`, and `BLOCKED`. Installing this release closes the caller-assertion path; it does not activate a human approval channel.

## Invariant and trust boundary

Work may execute only from verified first-party intake, or after a genuine human validates its external or unknown consumed inputs and accepted scope. A maintainer-created issue can project an external report, comment, attachment, or pull request; copying or summarizing that input preserves external lineage. Generic queue policy cannot waive human validation. Issue authors, owner association, labels, public markers, comment URLs, arbitrary authority references, and caller-written origin/approval fields are observations or assertions, never approval issuers. A shared GitHub account cannot distinguish a human from an agent using its token.

The previous failure chain was: supplied Authority reached Ready; the guard checked its limits but not its issuer; the application had no authenticated decision resolver; source records omitted consumed lineage; the host contract assumed trusted instructions that arbitrary CLI JSON could impersonate. The owning fixes are the admission/application boundary, dispatch boundary, and GitHub capture coordinator. Hashes bind exact recorded bytes; they do not authenticate the person who approved them. Keys or decision files that the consuming agent can mint or rewrite do not establish the missing boundary.

An embedding host can construct `WorkflowService(..., trusted_verifier=..., repository=...)`. Its narrow `TrustedIntakeVerifier.resolve(admission_id)` port must independently authenticate the intake or human event, establish complete consumed lineage, bind the intended repository, and return the live decision or deny it. No CLI argument, environment variable, plugin discovery, request JSON, or local signing utility supplies this port. Test controllers are explicitly synthetic and are not shipped as host adapters.

The host must gate external content before an executing agent consumes it. It must identify newly consumed material and the exact external PR head, including additions supplied outside the issue. The package cannot infer that a caller silently read a new attachment or commit; the verifier owns complete input provenance. The local process still runs as the user and is not an OS sandbox against a caller deliberately replacing the program or directly invoking an old binary.

## One immutable admission

The `intake_admission` record binds an opaque admission ID, repository, work ID, accepted scope hash, exact source object and source digest, allowed operations, expiry, revocation, decision kind and authenticated decision reference. `trusted_first_party` accepts only internal lineage established by the verifier. `human_validation` covers the exact external/unknown snapshot the human validated. The derived Authority uses those verified limits; a request's legacy Authority is never consulted as evidence of approval.

The source records a lineage array and its `consumed_digest`. Each consumed material has a kind, immutable repository/source/creator identifiers, exact revision, content digest, and observed origin. Issue title/body, consumed comments/attachments and external PR heads belong in this set. The source digest and accepted scope bind the whole set. Mutable presentation metadata and unrelated issue edits need no new approval when they were not consumed. Replaying an identical approved contract uses its frozen snapshot without fetching and importing later issue text.

`work ready` and `work amend` name `admission_id`; the trusted port supplies the record. An amendment needs a new immutable admission for changed scope or consumed material. Ready, Start, amendment, resumption, candidate/check work, action preparation/retry/begin and native handoff preparation share the same execution predicate. Check subprocess and external dispatch boundaries recheck it. Every new execution resolves the live decision, including expiry/revocation, and compares it with immutable history. A cached executable operation cannot revive old caller authority.

## Capture is bookkeeping

Capture retains the sanitized payload, optional `source_lineage`, immutable GitHub repository/issue/creator IDs, observed content digest and revision. It always records origin as unknown; even authenticated creation under our account establishes transport correlation, not first-party human intake. Reusing an issue is `reused_unknown`. A new created/read-back issue is `created_readback`. Neither grants execution authority. The trusted verifier independently validates lineage; capture flags cannot bless themselves.

Before POST, the coordinator journals expected repository and authenticated creator identities plus exact title/body digest. After a successful POST it durably records that response's exact issue identity before independently reading that issue. A later retry retains the response binding. If the response is lost, reconciliation requires a unique marker match plus the pending operation's expected repository, creator and exact content. A marker present before dispatch, multiple matches, wrong creator/content, or an uncertain absence fails closed. Reads never justify duplicating an uncertain write.

Confirmed legacy captures replay unchanged and remain unknown; missing provenance is never invented. Legacy pending captures without creation expectations cannot establish creation by their marker. Existing issue reuse remains a safe read. Caller-provided lineage is retained as evidence for later verification, including externally derived owner projections.

## Security exception to old runtime pins

The 0.2 entry point enforces admission before any old-runtime execution delegation and never delegates commands to older code. Historical package/profile/instruction snapshots remain readable and unchanged, but the current reader handles safe recovery. This intentionally overrides the earlier guarantee that active attempts continue executing their old pin: it would otherwise retain the vulnerable admission rules after upgrade.

Legacy Ready/Active work needs re-admission through `work amend` with an increased scope revision, complete lineage and a trusted decision before further execution. There is currently no production port to perform that re-admission. Reads, cancellation, blocking, accounting, finding observations and receipts remain available. Dispatched or ambiguous external actions can reconcile through read-only adapters without new authority; they are never redispatched. Resuming implementation or retrying a proven-unsent action requires current admission. Historical evidence is not deleted to make recovery look complete.

Regression tests cover default application/CLI denial, synthetic internal and exact-human external admission, forged refs/origin/approval, owned projections, changed consumed material/PR heads, all admission bindings, revocation/expiry, unchanged replay, old-pin attempts, copied/colliding markers, exact POST readback, lost responses, creator/content mismatches, and recovery without duplicate writes. Passing these tests proves the protocol and default denial, not deployment of an independent human channel.
